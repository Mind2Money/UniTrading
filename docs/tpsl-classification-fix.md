## 问题

- 现有 `protectionOrders()` 强制保护单含 `parentId`，漏掉以 `orderStrategy/orderStrategyLink` 描述的原生 ATM，以及没有父订单的 OCO 保护组合。
- 挂单列表将所有无 `parentId` 的 Limit/Stop 直接视作入场单；图表按该错误角色标记“拖动入场”。
- 现有同步没有订阅/保存策略与策略关联实体。

只使用用户提供截图与本地参考源码确认这些缺陷，不读取账户中的实际订单数据。参考的模拟例子位于 BatchTradovate 的 `tests/protection.test.mjs`、`tests/fake-broker.mjs`，均不是账户存档。

## 实施

1. 同步与归并 `orderStrategy` / `orderStrategyLink`。
2. 增加纯 Kotlin 订单分类器：
   - 使用同账户、同合约的父子关系、OCO 关联或单层 ATM 策略证据识别 SL/TP。
   - 不靠订单编号、价格高低或“反向单”独自认定保护；缺失、冲突、多级/多组关系保留为待确认，不冒充入场单。
   - 显示角色与是否可编辑分开。数量不匹配、部分成交待同步、非 Working 或关联不唯一时禁止保护拖动。
3. 在挂单模型中明确 ENTRY / STOP_LOSS / TAKE_PROFIT / UNRESOLVED；仓位记录保护订单 ID 及关联版本，防止旧编辑指向已替换的保护单。
4. 仓位 SL/TP、挂单表和图表共用分类结果，避免保护线重复绘制或出现“拖动入场”标签。
5. 保护单只进入保护价编辑路径；普通改单接口拒绝把保护单当入场单处理。分类更新自身绝不创建、撤销或修改任何订单。
6. 不自动纠正、补单、撤单、调整仓位或改变 OCO；原服务器记录保留，不伪造 parentId。

## 离线验收

- 支持原生父子保护、互指 OCO、共享 OCO ID；验证跨账户/跨合约不串联。
